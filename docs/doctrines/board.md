Composition and the board — the board definition, its verdict, its platform export. Part of the
partitioned project-doctrine registry: the bounded index is `DOCTRINE_ENFORCEMENT.md` ("This
project's own doctrines"), the registry of record is `scripts/check_doctrines.project.sh`, and
REGISTRY-MIRROR judges this family's union with its siblings as a mirror
(`LIVE-CONTAINMENT.3`).

## This project's own doctrines — board

| ID | Proves | Check |
| --- | --- | --- |
| `BOARD-GEN` | every map a board carries is still the byte-exact function of its canonical definition: the composition manifest, the four composed catalogues (materialized by `compose_units.compose_resolved` — the one code path the verdicts consume), the hardware description (`hardware.sexp`, schema-gated) and the human-readable map all regenerate from `profiles/<board>/board.sexp` by `scripts/gen_board.py` (OWN-05: no handwritten duplicate map anywhere; the freshness proof `compose_units.py` defers to the first tracked board). The generator refuses — by name — a region overlap, an mmio window with no device or a device with no window, an executable mmio region, or a console that is not a wired device; drift is refused with the regeneration command. The owner→mirror pairs are registered in `doctrine/fact_ownership.tsv`; fired RED before registration (`P5-BOARD.3`) | `scripts/check_board_gen.sh` |
| `BOARD-VERDICT` | a board's composition verdict is decided, not narrated (`docs/CPU_ENVIRONMENT.md` §5, ENV-02): `scripts/board_verdict.py` discharges every CPU environment-assumption in the composed unit against named guarantees, resolves every `satisfies` edge in the board definition to a discharged assumption, and binds every device obligation the dossier defers to the board (marked `composition_disposition "required"`) to exactly one board decision `answers` edge — with every `answers` naming a marked obligation. Any leg failing REJECTS the composition by name: an unmatched assumption is a rejection, never a note (`P5-BOARD.4`; self-test arms RED each leg on copies of the real board) | `scripts/check_board_verdict.sh` |
| `PLATFORM-GEN` | a board's platform capability manifest (`profiles/<board>/platform.sexp`, schema `schema/platform.sexp`) is still the byte-exact function of its canonical inputs: the board definition (boot contract and test-control surface included), the pinned processor's profile dossier, and the composed contract obligations — generated by `scripts/gen_platform.py` through the ONE board reader, the ONE dossier mapping and the ONE record mapping (OWN-06: derived, never handwritten — a compatibility checker imports facts rather than becoming a second hardware implementation, `docs/ARCHOGEN_INTEGRATION.md` §3). ⭐ The load-bearing extra: the board's `dossier-sha256` pin is verified against the live dossier at derivation time (`gate_report.dossier_digest`, the ONE computation) — the pin was measured display-only before this leaf, so a dossier edit could silently stale it; now the export refuses a stale pin by name. The generator refuses — naming the fact — a missing §3 value at its owner (endianness was prose-only until this leaf gave it a data owner), a boot/test-control claim the wiring contradicts, and an obligation parameter value it cannot emit (`P5-BOARD.6`; self-test 11 arms, every RED asserting its reason on copies of the real board) | `scripts/check_platform_gen.sh` |
