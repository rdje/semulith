# P3 — breadth, and the DSP pressure

**Deliverable: an abstraction that has been pushed on by something that is not a scalar CPU —
and an honest statement of what that proved.**

## Why now and not later

A cross-architecture API stabilised against one scalar CPU encodes that CPU's assumptions as if
they were universal: uniform operand widths, a single address space, instruction-level
atomicity, results visible at the end of the instruction. Real DSPs break all four. Discovering
that after the API is published means either a breaking change or a permanent workaround.

## What is actually done

1. **Review 15–20 discriminating cases** from real DSP specifications, chosen for properties
   those processors genuinely have — accumulator and guard widths, fractional scaling, where
   rounding happens relative to accumulation and narrowing, sticky flags across interrupts,
   instruction versus data address units, modulo and bit-reversed addressing, issue-group
   operand visibility, delayed results, hardware loops interacting with interrupts.
2. **Add executable synthetic tests** for nonstandard widths, distinct address spaces, packets,
   delayed effects, and register grouping.
3. **Select a narrow real DSP slice** only after demonstrating its evidence path — or publish a
   deliberately limited experimental claim instead.

## The honesty constraint

Synthetic behaviour tests the **interface**, not real DSP compatibility. A synthetic packet
fixture proves the API can express packets; it proves nothing about any manufacturer's part.

TI C64x/C64x+ is a *documentation* candidate. No runnable oracle access has been established,
and its availability is resolved before any compatibility release is promised.

## Gate BREADTH

The stated real subset has evidence; the public abstraction supports the exercised cases;
unsupported families remain unclaimed. A stable general API requires this gate —
architecture-specific CPU progress does not.
