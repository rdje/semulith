# P5–P7 — board, Linux, computer

## P5 — model one board in Rust

A minimal virtual platform with documented memory, reset, timers, interrupt controllers, and a
serial console. Each device gets a dossier, requirement and evidence links, and state, reset,
and access tests — devices reuse the same machinery as the CPU, they are not a lower tier.

The composition obligation is the interesting one: **for every CPU assumption, identify the
board or device guarantee that satisfies it, or reject the composition.** Reset wiring, memory
attributes, source priorities, counter units, time progress, access side effects, reservation
invalidations, instruction visibility. A model mismatch found later becomes a CPU, contract,
device, or composition issue with explicit ownership — never an unattributed "emulator bug".

Address maps, wiring, and hardware-description data are generated from the canonical board
definition. Device behaviour stays owned by the device definition.

**Gate BOARD:** devices and composition pass their applicable gates; small firmware probes
pass; no silently incompatible CPU/environment assumption remains.

### The first board, specified: `netboard-lab-v0` (EXPERIMENTAL)

The platform specification is done (`P5-BOARD.1`, `2026-10-02`): the canonical definition is
`profiles/netboard-lab-v0/board.sexp`, gated by `schema/board.sexp` and narrated by the
dossier's `DOSSIER.md`. It composes `rv64i-lab-v0` v0 — the EXPERIMENTAL CPU release, whose
status the board inherits — with exactly two devices, and it **pins versions, not names**:
the processor by unit id + version + the GATE-REPORT-gated dossier content digest, each
device by its datasheet's material id + revision + sha256.

- **Memory map:** 2 GiB RAM at `0x8000_0000` (the laboratory harness's existing base, so
  laboratory guests run unchanged); the SiFive UART at `0x1001_0000` (the sourced FU540-C000
  instance address); the LAN9118 NIC in a 256-byte window at `0x1002_0000` (the datasheet's
  direct-register span). Fetch is served from RAM only — every MMIO region is declared
  non-executable, so no fetch can have a side effect.
- **Reset:** cold only; the entry state is the CPU contract's, cited not restated.
- **Timers and interrupt controllers are absent by contract** — declared as data with the
  obligations the absences satisfy (`OB-ENV-VIRTUAL-TIME`, `OB-ENV-EVENT-DELIVERY`). A
  CLINT/PLIC would be a composition rejection, not a feature; both devices' interrupt lines
  are unconnected and declared so, and drivers poll.
- **The network device is the board's window on the world from v0:** the LAN9118 is
  programmed-I/O (no bus-master DMA), so every device effect reaches the guest through its
  own MMIO accesses. Receive is recorded-trace replay (deterministic, evidence-grade);
  transmit is a recording sink; a live host socket stays laboratory play, never evidence.

One measured correction landed with the specification: the serial device is the **SiFive
UART** of FU540-C000 §13, not a 16550 — the earlier label survived a design brief and was
measured false against the pinned PDF (zero occurrences of "16550" in the document) before
it could ossify into a device dossier. The source pin, not the label, was the intent.

Device dossiers follow one device per leaf — the UART first (`.2`, done `2026-10-02`),
the LAN9118 second (`.10`, done `2026-10-02`); all three units registered together on
registration day (`.11`, done `2026-10-02` — the registry's `kind` learned `board` and
`device`, and each unit's own book builds under `docs/models/`); the generated maps
(`.3`, done `2026-10-02`) and the composition verdict against every CPU assumption
(`.4`, done `2026-10-02` — **ACCEPTED**, below) followed. The platform capability
manifest (`.6`) is the remaining pre-gate work; the probes (`.5`) and the `BOARD` gate
report (`.7`) stay gated on the CPU's acceptance trajectory.

### The first device dossier: `sifive-uart-lab-v0` (EXPERIMENTAL)

The SiFive UART's dossier (`profiles/sifive-uart-lab-v0/`) reuses the CPU's dossier
machinery in full — no lower tier: pinned source (FU540-C000 v1p5 §13, digest-verified),
13 defined + 6 unspecified requirement records, the mirrored contract obligations
(`sifive-uart-v0` v0 — the schema's new third direction, `device-guarantee`), the state
document with its earned hidden-state census (the model carries the seven registers and
the two FIFOs' contents and occupancies, and nothing else an MMIO access can reach), and
datasheet-derived register-read expectations recorded **before any model exists** —
including the X-marked reset values deliberately left unpinned.

The dossier generalised the machinery, by declaration rather than exemption: a unit's
`vehicle` block now admits `(route device-model)` with `(comparison
register-expectations)`, and the instruction-shaped gates (EXTRACTION, EXERCISE-COVERAGE,
INTERACTION-MATRIX) derive their applicability from the declaration — a document
contradicting it (an encoding space, a guest corpus) is a finding, not a pass
(`decision_device-applicability-by-declared-vehicle`). A device guarantee discharges a CPU
assumption by construction in the composition checker, pinned by a self-test arm.

One measured finding shaped the dossier: §13.8's watermark bits have a strict-inequality
*raised* condition and a strict-inequality *cleared* condition, and the manual never says
whether the bit is a pure level of FIFO occupancy or holds between the two — the `==`
boundary and any pre-first-condition value are undetermined (`REQ-D-UART-WM-MODE`), so the
expected results pin a watermark bit only when its raised condition holds under every
reading. A polled driver drains `rxdata` to empty and fills `txdata` to full instead of
trusting the bit at the boundary.

### The second device dossier: `lan9118-lab-v0` (EXPERIMENTAL)

The LAN9118 NIC's dossier (`profiles/lan9118-lab-v0/`) inherits the hardened device shape
with **no machinery edit** — the by-declaration generalization already covers it — and
the contract is much larger than the UART's: 52 mirrored records (46 datasheet-defined,
plus the measured silences and deferrals), 49 registers across three indexing levels
(direct CSRs, the MAC CSR synchronizer, the MII PHY bridge), the four FIFOs, and three
expectation documents derived from the datasheet before any model exists — cold-reset
register reads, exact TX free-space accounting (§3.12.5's rules make TDFREE arithmetic
pinable without a wire), and the recorded-trace RX path (status-word format, pop/PEEK
semantics, the underrun → RXE → soft-reset discipline).

Two measured findings shape the composition work ahead. **The NIC carries guest-readable
time sources** — a free-running 25 MHz counter, a 100 µs timer readout, a 10 µs interrupt
deassertion interval — and the CPU contract excludes every guest-reachable time source,
so the model must freeze them deterministically rather than wire them to wall-clock
(`REQ-D-NIC-TIME-SOURCES`, pre-wiring `.4`'s verdict). And the pinned datasheet's own
text layer mis-renders §3.11's soft-reset completion times (`2 s` where the same document
elsewhere says `100us` for the same PHY reset) — the dossier pins only the cleanly stated
figures (`REQ-D-NIC-RESETS`). The dossier's scale also moved the `profiles/` family's
per-part bound for the first time (32 KiB → 64 KiB, reviewed and recorded:
`decision_profiles-family-five-units`).

### The generated maps: one definition, seven derived artifacts

With the three units registered, the board's maps stopped being prose. `scripts/gen_board.py`
derives everything downstream of `board.sexp` (OWN-05 — no handwritten duplicate map
anywhere): the **composition manifest** (the part list derived from the pins, not
restated), the four **composed catalogues** (99 requirements, 107 obligations, 5 sources
and the encoding — materialized by `compose_units.compose_resolved`, the one code path
the composition verdict consumes, so `.4`'s input is on disk and freshness-gated), the
**hardware description** (`hardware.sexp`, under its own schema: every region resolved
with its computed end, the device↔region↔width↔backend wiring, the console, the reset,
the declared absences with their `satisfies` edges), and the human-readable **map** (the
chapter you can read in the board's own book — one generated file, included).

The drift gate is the **BOARD-GEN** doctrine: it re-derives all seven artifacts on every
commit and refuses, naming the artifact — the freshness proof `compose_units.py` had
deferred to the first tracked board. The generator itself refuses an inconsistent
definition by name (a region overlap, an MMIO window with no device, an executable MMIO
region), so a broken map can never be generated in the first place. The one handwritten
duplicate the census found — the DOSSIER's own map table — was replaced by the generated
map; the dossier now narrates the choices and links the data.

### The composition verdict: every assumption matched, or rejected

The gate's core obligation (`.4`, done `2026-10-02`): for **every** CPU environment
assumption, the board or device guarantee that satisfies it — or a rejection. The verdict
is **ACCEPTED**, and it is decided, not narrated: the **BOARD-VERDICT** doctrine
(`scripts/board_verdict.py`, re-run on every commit) discharges all eight assumptions
over the composed catalogues, resolves every `satisfies` edge in the board definition to
a discharged assumption, and binds every device obligation the dossier defers to the
board (marked `composition_disposition "required"`) to exactly one board decision
`answers` edge — an unmatched assumption or a dangling edge is a **rejection by name**,
never a note.

The discharge edges alone would pass with a CLINT bolted on — they key on obligation
ids, and the platform-dependent two land on `OB-PLATFORM`, the *laboratory* guarantee.
What makes the composition hold on the board is the content half, declared as data: the
timer/interrupt-controller absences (`satisfies`), and the four composition
**dispositions** the verdict decides (board decisions, mirrored into `hardware.sexp` for
the model route): the NIC's straps (D32 tied high — 32-bit native mode; SPEED_SEL at its
pull-up), its guest-readable time sources **frozen** (constant values carry no time
information, so `OB-ENV-VIRTUAL-TIME` holds with the NIC present), the replay's link
scene **static and complete** at 100BASE-TX full-duplex (the cold reset completes before
any guest access, so Note 3-11's wait-for-link succeeds at the first read), and the pin
reads **tied off at 0**. The verdict also caught a real defect: the board had declared
16-bit accesses for the NIC from the datasheet's summary sentence, but §3.6 makes the bus
widths mode-exclusive — with D32 strapped, the declaration narrows to 32 only.
`MODEL-COMPOSE`'s open question — does a board need an operator beyond union and
discharge? — is answered for this board shape: no; the declared edges close the gap. The
authored half is `profiles/netboard-lab-v0/COMPOSITION-VERDICT.md`,
included as the board book's verdict chapter; the interface-test leg re-ran the
laboratory's boundary and fixture suites (green — the RAM half the board preserves;
the MMIO halves attach with the device models).

### The archogen branch

At this point a compatible archogen-generated OS may enter its own integration gate without
waiting for Linux or the full computer. Its required CPU profile must already have passed a CPU
gate; if it needs fewer features than P4, a separately accepted smaller profile can support an
earlier board branch under the same rule.

## P6 — boot Linux to useful userspace

Pin the firmware, the kernel, the build configuration, the hardware description, and the
initramfs. The default RISC-V route executes compatible M-mode firmware providing selected SBI
services before entering an S-mode kernel. A host-modelled SBI is a *different contract* and is
never silently substituted for it.

**Gate LINUX:** a reproducible cold boot reaches userspace `init` and a console shell, runs a
guest program, exercises timer-driven scheduling, and completes a documented shutdown or reboot
path. A kernel banner is not a pass.

CPU bugs discovered here return to CPU regressions and **invalidate affected evidence**. Booting
does not retroactively prove the CPU; failing to boot does prove something was wrong.

## P7 — a useful headless computer

Without this increment the project has validated parts, not a computer: P7 is where the
machine becomes something a workload can *use*.

Persistent block storage, file workloads, networking, reset and reboot, and system snapshots —
each as an individually specified increment with reproducible guest workloads and device
evidence.

**Gate SYSTEM:** the declared headless workload suite passes, storage persists correctly, and
snapshot/restore preserves the relevant CPU, device, and event state. This is the first bounded
full-computer release.

Graphics, input, and a desktop are a **subsequent** product increment with their own device list
and performance budget — kept visible rather than hidden inside P7.
