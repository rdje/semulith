# P0 — profile and evidence access

**Deliverable: knowing exactly what we are modelling, and proving we can obtain expected
results for it.**

## The profile

Create `rv64i-lab-v0` as a *development* profile: RV64I semantics, one core, little-endian
ordinary memory, an explicit entry state, memory boundaries, an access and misalignment policy,
instruction-fetch rules, and environment-trap reporting. Pin the applicable specification
revision and resolve every choice the selected scope needs.

No privileged-system support is implied by any of that. Selecting RV64I is not a claim that the
laboratory already constitutes a fully specified privileged processor — it is the smallest
scope in which real scalar machinery can be validated at 64 bits without a 32-bit detour.

## The part that is easy to skip

Acquire reproducible source or binary builds for the chosen reference path, and **run at least
one actual matched-profile experiment before marking that reference usable**. Record tool
versions, source and binary hashes, effective configurations, adapters, and known gaps. Then
establish whether a second comparator shares relevant semantic code with the first.

That last sentence is the one that does the work. Two tools with different names are not two
opinions if their expected results come from the same model. Three facts already known:

- the RISC-V architectural tests use **ACT4**, which computes expected results with a
  *configured Sail* model — valuable external tests, not a second semantics;
- **TestFloat** ordinarily obtains its expected values from **SoftFloat**, so comparing against
  SoftFloat directly is not automatically another independent numerical engine;
- **Spike** is a different implementation path, but its subsystems' independence has to be
  examined rather than inferred from the project name.

## What acquisition actually found

That section was written as a plan. Here is what happened when it was executed.

**Three reference models were obtained and run on this host**, and one test corpus was located
and deliberately left alone:

| Candidate | How it was obtained | Configured to this profile by | Reports itself as |
| --- | --- | --- | --- |
| Sail RISC-V 0.14 | prebuilt `Mac-arm64` release binary | a tracked JSON override | `rv64i_zvl32b` |
| Spike 1.1.1-dev | source build, commit `1e05ddac` | `--isa=rv64i --priv=m` | `rv64i` |
| QEMU 11.1.1 | already on the host; used read-only | `-cpu rv64i` | *(emits no ISA string)* |
| ACT (`act4` branch) | reachable, not acquired | — | — |

**The budget was wrong in the project's favour.** The plan priced this work on building Sail
from source through an OCaml/opam toolchain, which is genuinely open-ended. Release 0.14
publishes a native binary for this host's exact architecture, so the model runs with no toolchain
at all. Sail turned out to be the *cheapest* candidate, not the most expensive one.

**One attempt failed, and the failure is the interesting one.** The host package manager has a
formula called `sail`. It is a CLI for deploying WordPress sites to DigitalOcean — an exact name
collision with the Sail ISA specification language. Identity was checked rather than assumed, and
the check is the only reason "Sail is available from the package manager" was not written down as
a fact. This is `SRC-03` earning its place: a candidate list is the easiest document in a project
to fill in from reputation.

### Three models is not three opinions

The plan already warned about this and the acquisition confirmed it in writing. ACT computes its
expected results using a *configured Sail model*, so ACT agreeing with Sail is one semantics
answering twice. Spike and QEMU were written independently of Sail and of each other — *plausibly*,
which is a hypothesis, not a finding. Every candidate record carries a `lineage` field stating
what is known and what is not, and the gate **refuses a candidate that omits it**, because an
independence question nobody asked reads exactly like one that was answered.

Resolving it per subsystem is a separate leaf. Having the binaries is not having the evidence.

### Two differences are already known, before a single instruction has run

The gate asks for profile and reference differences to be **enumerated, not assumed absent**. Two
turned up during configuration alone:

*The Sail model cannot be configured down to exactly "no extensions."* From a default of 96
supported extensions it reaches `rv64i_zvl32b` — the base plus a vestigial minimum vector-length
class that survives because the model always instantiates a `VLEN` even with the vector unit
disabled. No vector instruction decodes, so it is believed harmless. It is recorded anyway,
because "believed harmless" and "absent" are different words.

*The Sail model will not report the configuration it actually ran with.* Asking it to print its
configuration prints the **default**, ignoring the override — the two dumps are byte-identical.
The effective configuration is therefore *(default) + (our tracked override)*, and that merge is
**ours, not the model's account of itself**. The one thing the model does say about itself is its
ISA string, which is why `rv64i_zvl32b` is pinned and re-derived on demand. The smoke test may
not quietly upgrade our merge into the model's own word.

### Nothing here says a reference is usable

A reference becomes usable when a real matched-profile experiment has been run against it and
reproduced — not when its binary exists. What this work establishes is deliberately narrower:
*we have these binaries, this is exactly which ones they are, and each can be configured to
something close to this profile.* The experiment is the next leaf, and the difference between
those two sentences is most of what this milestone is about.
