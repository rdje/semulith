# P4 — the Linux CPU profile

**Deliverable: the processor Linux actually needs, validated as a processor.**

Select a Linux-capable profile — provisionally RV64GC with an explicitly chosen privilege
revision, M/S/U modes, Sv39 translation, implemented CSRs, interrupt acceptance, counter
behaviour, and stated firmware and toolchain requirements. *Provisionally* is load-bearing:
the exact dependency closure is resolved before the profile is claimed, not assumed from the
letters.

## The new work

System transitions, page walks and their permitted side effects, protection, atomics, floating
point, instruction visibility, faults, and restart obligations — all implemented and
independently tested **in the laboratory environment**, not by booting something and seeing
whether it complains.

## The floating-point condition

Floating-point support is not included until a named Rust implementation has passed its own
qualification task: the exact target policy for rounding modes, flags, result bits,
conversions, NaN payloads and boxing; the ancestry inventory (shared SoftFloat lineage, target
specialization, thread-local versus global status handling, exact compiler and features); and
independent numeric fixtures.

If no suitable Rust implementation passes, the required subset is implemented in Rust and the
corresponding CPU capability is deferred until validated. There is **no silent native-float or
FFI fallback** — that would make the host's floating-point defaults into the guest's semantics.

## The profile, resolved: `rv64gc-lab-v0` (`P4-SYSTEM.1`, 2026-10-03)

The provisional letters are now an exact, source-located selection. RV64I plus **M, A, F, D,
C, Zicntr, Zicsr, Zifencei**, with **Sstc** on the privileged side — ISA string
`rv64imafdc_zicntr_zicsr_zifencei_sstc`, amended at `.3` slice (a) to
`rv64imafdc_zicntr_zicsr_zifencei_sstc_svade` (**Svade** selected: a translation needing
an A/D PTE update page-faults, never a hardware update); **M/S/U** modes; **Sv39**
translation; IALIGN 16
(with C) and ILEN 32; one hart; a committed minimum of 33 CSRs; the LP64D toolchain ABI; and
SBI 2.0 as the firmware contract the P6 boot route will execute. Every element cites the
pinned publication: the pinned v20260120 snapshot was measured to *carry* the privileged
chapters (24 `priv/` + 46 `unpriv/` pages, every cited row re-hashed against the tracked
`SHA256SUMS`), so the privileged evidence base is citable today — a 2026-09-27 census note
that called the privileged volume "absent from this snapshot" is measured false and
superseded.

The dependency closure is measured, not inferred: G = IMAFD + Zicsr + Zifencei (the naming
chapter's own definition), D depends on F, F depends on Zicsr, and C decomposes as Zca plus
Zcd at RV64 with D. The floating-point condition above becomes concrete in the resolution:
F and D are **in** the profile because the standard RV64G userspace ABI (LP64D) requires D —
and the model implements none of it until `P4-SYSTEM.7` qualifies a backend; the CPU-SYSTEM
verdict reads `incomplete` until then, and Sail-versus-Spike is one SoftFloat implementation
twice, never independent numeric evidence.

The unit (`profiles/rv64gc-lab-v0/`) is deliberately **unregistered** and declares the new
`profile-resolution` vehicle route: the selection is exact and citable, the definition
pipeline starts at `.2`, and the pipeline gates refuse any encoding, state-census or
guest-corpus document beside the declaration.

## What the gate still needs (planned 2026-10-06)

Before writing the gate report, the project measured what evidence the Linux-capable profile
actually has on each of the processor gate's ten axes. Most of the hard work is done, but the
measurement found real gaps that the earlier plan had not given an owner:

- **Two declared extensions are not modelled yet.** Integer multiply/divide (M) and the
  compressed 16-bit instructions (C) are part of the selected profile, but their definitions
  were never bound into the processor. An earlier plan pointed at "their leaves", and those
  leaves were never created.
- **The tooling around the processor is still scalar-only.** Snapshots, replay bundles, the
  case reducer, the deliberate-mutation suite, the external test campaign and the cross-host
  portability check all exist for the scalar profile, and none of them runs on this one yet.
- **The evidence is real but not yet in record form.** Seven comparison experiments against
  the Sail reference model were run and written up as prose, but no gate checks prose, and
  every requirement still reads "planned" even where it has been implemented and tested.
- **The contract is not complete.** The scalar profile's basic assumptions about memory and
  reset were never restated for this profile, and a few frozen statements have gone out of
  date.

So the gate report (`.10`) is built first, as an **instrument**. It measures each axis from
the profile's own files and refuses to say "passed" while any axis is open. Eight new leaves
then close the axes one at a time, in an order that measures each axis once over the complete
profile:

- `.11` and `.12` bind M and C.
- `.13` completes the contract.
- `.14` turns the experiments into records and derives each requirement's status from its
  evidence.
- `.15`, `.16` and `.17` bring regression, replay and portability to this profile.
- `.18` reads the final verdict and records the release decision.

## Gate CPU-SYSTEM

The complete declared profile passes the processor gate, including its environment contract.
This gate authorises board implementation. It does not require a new permission ceremony — it
*is* the permission.
